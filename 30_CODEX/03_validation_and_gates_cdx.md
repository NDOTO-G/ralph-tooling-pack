# Validation & Gates – Codex CLI

Because Codex lacks native hooks or a `maxSteps` parameter, the Ralph harness must implement its own validation and gating logic.  This ensures that each iteration meets quality standards before proceeding.

## Validation strategies

* **Run tests manually** – After each `codex exec`, execute your test suite using a separate command (e.g., `npm test`).  If tests fail, parse the output and feed the errors back into the next prompt (e.g., “The tests failed with the following errors … fix them”).
* **Inspect JSON events** – The `item.*` events in the JSON stream include diffs and command executions.  Analyse these to detect unexpected file edits or command failures.  Treat any `error` event as a validation failure.
* **Format and lint** – Run linters and formatters outside of Codex (or via a separate agent) to enforce style guidelines.  Alternatively, implement a `$lint` skill and invoke it in a follow‑up prompt.
* **Diff review** – Use another agent (e.g., Claude or a review skill) to evaluate the diff generated by Codex.  Ask the reviewer to comment on potential issues or missing edge cases.

## Approval gating

Codex delegates shell execution to its internal tools.  Use the following mechanisms to control what commands it runs:

* **`--ask-for-approval`** – Choose how often Codex prompts for approval (`untrusted`, `on-failure`, `on-request`, `never`)【413965132490193†L233-L287】.  In unattended runs, `on-request` is a safe default; it only asks when the model explicitly requests approval.
* **`--sandbox`** – Restrict write access with `read-only` or `workspace-write` modes.  Avoid `danger-full-access` unless you run in a disposable environment【413965132490193†L418-L427】.
* **`.rules` files** – Define `prefix_rule` functions in `~/.codex/rules` to allow, prompt or forbid specific command patterns【40854120253895†L214-L280】.  For example, forbid `rm -rf` or always require approval for `gh pr merge`.

## Retrying and escalation

If validation fails or the agent appears stuck:

1. **Retry** – Provide additional context or narrower instructions in a new prompt.  Mention test failures or highlight specific functions to modify.  Limit retries to avoid burning tokens.
2. **Escalate** – Switch to a more capable model or a different tool (e.g., Claude Code) after repeated failures.  Alternatively, request human intervention.
3. **Abort** – After hitting `max_failures` or `max_iterations`, record an escalation entry in the progress log and stop the job.

By building these gates into the harness, you mitigate the absence of native hooks in Codex and maintain control over its actions.
