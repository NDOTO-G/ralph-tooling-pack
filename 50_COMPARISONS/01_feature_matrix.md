# Feature Matrix

The table below compares key capabilities across the three agent runtimes (OpenCode, Codex CLI and Claude Code) as they pertain to a Ralph harness.

| Capability | OpenCode | Codex CLI | Claude Code |
|---|---|---|---|
| **Headless automation friendliness** | Designed for both interactive and headless use; `opencode run` with `--format json` streams structured events and integrates with `opencode serve` for warm sessions【674709478433772†L420-L449】. | Supports non‑interactive runs via `codex exec` which prints only the final assistant message; add `--json` to stream JSON events【874755510451889†L214-L242】. | Headless mode via `claude -p`; supports `--output-format stream-json` but disables slash commands and interactive skills【649120918286103†L66-L90】. |
| **Skill system maturity** | Rich skill system: skills live in `.opencode/skills/`; loaded hierarchically; YAML front‑matter defines name, description, compatibility and metadata【474358579328195†L119-L129】. Skills invoked via the `skill` tool call【474358579328195†L195-L215】. | Skills captured in `SKILL.md` per folder; loaded from multiple scopes (project, repo, user)【317920800239899†L260-L291】. Invocation via slash commands or `$skill` tokens【317920800239899†L213-L259】. | Skills live in `.claude/skills/` with YAML front‑matter; support advanced fields (`disable-model-invocation`, `allowed-tools`, `context: fork`)【500585924894070†L290-L318】.  In headless mode skills must be inlined; slash commands are disabled【649120918286103†L193-L195】. |
| **Native hook support** | Yes – plugin system with extensive event hooks (`tool.execute.before/after`, session events, permission events, file events, compaction events).  Plugins are loaded from project or user directories and can modify tool input, log events or abort actions【543225958782144†L170-L336】. | No first‑class plugin API; uses a rules engine (.rules files) to allow, prompt or forbid commands【40854120253895†L214-L280】.  Supports `notify` hook in config to call a script on `agent-turn-complete`【454175575763456†L564-L603】. | Yes – configurable hook mechanism; shell commands can be bound to events like PreToolUse, PostToolUse, PermissionRequest, Notification and PreCompact【995113787448290†L100-L119】.  Hooks run automatically and must be secured to avoid leakage【995113787448290†L90-L94】. |
| **Stop/budget controls** | Exposes `maxSteps` in agent configuration to cap tool calls【559550733105805†L491-L524】.  Environment variables like `OPENCODE_EXPERIMENTAL_OUTPUT_TOKEN_MAX` and bash timeouts further constrain execution【674709478433772†L710-L717】. | No intrinsic step limit; budgets enforced by harness.  Use `--sandbox` and `--ask-for-approval` to limit what can be run【413965132490193†L220-L287】.  Token usage monitored externally via cost dashboards. | No built‑in step limit or budget control.  Harness must impose iteration/time/token budgets and detect completion via sentinels and validation. |
| **Permission/sandbox posture** | Fine‑grained permission model; patterns to `allow`, `deny` or `ask` for tools and skills【474358579328195†L218-L247】; doom loop and external directory guards provide safety【310356558666353†L193-L214】. | Sandbox defaults to read‑only; `--sandbox workspace-write` or `danger-full-access` change scope【413965132490193†L772-L801】.  Approval policy controlled by `--ask-for-approval` and `.rules` files【413965132490193†L220-L287】. | Permissions enforced via interactive prompts; headless runs rely on `--allowedTools` to pre‑approve tools【649120918286103†L161-L173】.  Dangerously skipping permissions is possible but discouraged【135116144821332†L299-L309】. |
| **MCP/document access strategy** | Supports Model Context Protocol servers; defined in `mcp` section of `opencode.json`; can run local or remote servers to augment capabilities【605040260244603†L195-L223】. | Not applicable; relies on built‑in tools and skills.  Integration with external services requires custom wrapper tools run via Bash. | Supports MCP connectors (e.g. Puppeteer, GitHub) for extended capabilities; configure via `.claude/settings.json` and environment variables.  Only enable connectors needed for the job. |
| **Free/local model routing** | Not built‑in; always uses provider endpoints (Anthropic, etc.).  Could theoretically run open source models via a custom MCP server but not officially supported. | Yes – the `--oss` flag routes to a local provider (requires an Ollama/LM Studio server)【413965132490193†L892-L904】. | No built‑in local model support.  Only Anthropic hosted models are available. |
| **Best‑fit role in Ralph** | **Primary runner:** headless JSON mode with warm server is efficient.  Rich skills and plugins make it ideal for large codebases and unattended tasks. | **Cost‑sensitive runner:** non‑interactive runs with local models via `--oss` are good for offline or budget‑constrained tasks.  Lacks hooks, so rely on harness for validation. | **Escalation/reviewer:** strong reasoning and context management.  Use as a fallback when OpenCode or Codex stalls or for complex code reviews.  Hooks support notifications and policy enforcement. |

This matrix highlights that no single tool is perfect for all situations.  A robust Ralph harness should dynamically select the engine based on task complexity, cost constraints and required safety guarantees.
